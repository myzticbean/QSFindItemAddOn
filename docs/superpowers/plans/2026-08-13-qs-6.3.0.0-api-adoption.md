# QuickShop-Hikari 6.3.0.0 API Adoption — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Adopt the QuickShop-Hikari 6.3.0.0 inventory-count-cache and async-stock APIs so shop stock/space reads stop force-loading chunks and stop blocking virtual threads, and migrate off the deprecated `Shop#getPrice()`.

**Architecture:** All three tasks touch a single file, `QSHikariAPIHandler`, and specifically the stock/space read path used by `/finditem` searches. Task 1 introduces a resolution ladder (unlimited → live read if chunk loaded → QuickShop's persisted inventory count cache → force-load as last resort) that replaces today's unconditional chunk force-load. Task 2 converts that ladder to a fully non-blocking `CompletableFuture` chain built on the new `ShopInventory#getRemainingStockAsync()`. Task 3 migrates the two `getPrice()` call sites to `ShopPrice#price()` behind a single contained unchecked cast.

**Tech Stack:** Java 25, Maven, Paper API 26.2, QuickShop-Hikari API 6.3.0.0-SNAPSHOT-12, FoliaLib (`PlatformScheduler`), project-local `VirtualThreadScheduler`.

### Background: why these changes are correct

Read this before touching code; the reasoning is not obvious from the QuickShop changelog and several of the sharp edges below are not documented anywhere.

In QuickShop-Hikari 6.3.0.0, `ContainerShop` implements these two methods very differently:

- **`getRemainingStock()`** is now `getRemainingStockAsync().orTimeout(5, SECONDS).exceptionally(ex -> 0).join()`. `getRemainingStockAsync()` returns `-1` immediately for unlimited shops; otherwise, if the caller is not on the shop's owning region it schedules a `runAtLocation` task. That task calls `getInventory()`, **which returns `null` when the shop's chunk is unloaded**, so `calculateRemainingStock()` yields `0`. It no longer consults the inventory count cache at all.
- **`getRemainingSpace()`** is still synchronous. When the caller is not on the owning region it returns `Math.max(inventoryCountCache.getSpace(), 0)` — the in-memory count cache, clamped. Because our search runs on virtual threads, we are *always* off-region, so today we never get a live space read.

The in-memory count cache is seeded at shop load from a `LEFT JOIN` on the `external_cache` table and is kept current by `InternalListener#shopInventoryCalc`, which listens for `ShopInventoryCalculateEvent`.

**The sharp edge:** `ContainerShop` fires that event as `new ShopInventoryCalculateEvent(this, -1, stock)` from the stock path and `new ShopInventoryCalculateEvent(this, space, -1)` from the space path. The listener writes both fields unconditionally. **So each calculation clobbers the other field with `-1`.** The persisted cache can only hold one meaningful value at a time — whichever was computed most recently.

This is why the code you are about to write must treat any negative value from the count cache as *unknown* and fall through, rather than trusting it. It is also why `getRemainingSpace()` can legitimately return `0` for a well-stocked shop (cache holds `-1` from a stock calc, `Math.max` clamps it to `0`) — a live instance of the issue #111 symptom that our current force-load happens to paper over.

The API sentinels, per `ShopInventoryCountCache`'s javadoc: `-1` = never calculated **or unlimited shop**, `-2` = not yet persisted to the database. Both are `< 0`, so a single `>= 0` test covers "usable". We short-circuit unlimited shops *before* consulting the cache, which removes the `-1` ambiguity entirely.

```java
    /**
     * Reads the shop's stock/space from QuickShop's persisted inventory count cache
     * ({@code external_cache} table), which is populated whenever QuickShop calculates a shop's
     * inventory and survives the chunk being unloaded.
     * <p>
     * QuickShop documents two negative sentinels on {@link ShopInventoryCountCache}: {@code -1} for
     * "never calculated or unlimited shop" and {@code -2} for "not cached into database yet".
     * A third case produces a negative value in practice: QuickShop's own
     * {@code InternalListener#shopInventoryCalc} writes both stock and space on every
     * {@code ShopInventoryCalculateEvent}, and {@code ContainerShop} fires that event with
     * {@code -1} in whichever field it did not just compute - so a stock calculation clobbers the
     * cached space and vice versa. Any negative value therefore means "unusable, ask someone else",
     * which is exactly what the {@code >= 0} test at the call site expresses.
     *
     * @return the cached stock or space, or a negative value if it is unknown/unusable
     */
    private int readStockOrSpaceFromQsCountCache(Shop shop, boolean toBuy) {
        try {
            ShopInventoryCountCache countCache = api.getShopManager()
                    .queryShopInventoryCacheInDatabase(shop)
                    .orTimeout(INVENTORY_COUNT_CACHE_TIMEOUT_SECONDS, TimeUnit.SECONDS)
                    .join();
            if (!countCache.initialized()) {
                Logger.logDebugInfo("QS inventory count cache not initialized for shop: " + shop.getShopId());
                return -2;
            }
            int cachedValue = (toBuy ? countCache.getStock() : countCache.getSpace());
            Logger.logDebugInfo("QS inventory count cache for shop " + shop.getShopId() + ": " + cachedValue);
            return cachedValue;
        } catch (Exception e) {
            Logger.logDebugInfo("Failed to read QS inventory count cache for shop " + shop.getShopId()
                    + ": " + e.getClass().getSimpleName() + " - " + e.getMessage());
            return -2;
        }
    }
```

```java
    /**
     * Resolves a matched shop's remaining stock (when buying) or space (when selling), in order of
     * decreasing preference:
     * <ol>
     *   <li>Unlimited shops short-circuit to {@code -1}, which
     *       {@link QSApi#processStockOrSpace(int)} maps to {@link Integer#MAX_VALUE}. Doing this
     *       first also removes the ambiguity in QuickShop's {@code -1} count-cache sentinel, which
     *       conflates "unlimited" with "never calculated".</li>
     *   <li>If the shop's chunk is loaded, read it live - this is the accurate path and costs
     *       nothing extra.</li>
     *   <li>Otherwise consult QuickShop's persisted inventory count cache, which is exactly what it
     *       exists for and needs no chunk.</li>
     *   <li>Only if the cache has nothing usable, force-load the chunk (see issue #111). This is
     *       the expensive path and is now rare.</li>
     * </ol>
     */
    private int resolveStockOrSpace(Shop shop, boolean toBuy) {
        if (shop.isUnlimited()) {
            return -1;
        }
        if (isShopChunkLoaded(shop)) {
            return getRemainingStockOrSpaceFromShopCache(shop, toBuy);
        }
        int cachedValue = readStockOrSpaceFromQsCountCache(shop, toBuy);
        if (cachedValue >= 0) {
            return cachedValue;
        }
        Logger.logDebugInfo("Falling back to chunk force-load for shop: " + shop.getShopId());
        return fetchLiveStockOrSpaceForUnloadedChunk(shop, toBuy);
    }
```

## Task 2: Make the stock/space read path fully non-blocking

```java
     * completed the upstream stage - which for QuickShop's async APIs is a region thread or a
```

```java
     * ({@code external_cache} table), which is populated whenever QuickShop calculates a shop's
     * inventory and survives the chunk being unloaded.
     * <p>
     * QuickShop documents two negative sentinels on {@link ShopInventoryCountCache}: {@code -1} for
     * "never calculated or unlimited shop" and {@code -2} for "not cached into database yet".
     * A third case produces a negative value in practice: QuickShop's own
     * {@code InternalListener#shopInventoryCalc} writes both stock and space on every
     * {@code ShopInventoryCalculateEvent}, and {@code ContainerShop} fires that event with
     * {@code -1} in whichever field it did not just compute - so a stock calculation clobbers the
     * cached space and vice versa. Any negative value therefore means "unusable, ask someone else",
     * which is exactly what the {@code >= 0} test at the call site expresses.
     *
     * @return a future of the cached stock or space, or of a negative value if it is unknown
     */
    private CompletableFuture<Integer> readStockOrSpaceFromQsCountCacheAsync(Shop shop, boolean toBuy) {
```

```java
     * decreasing preference:
     * <ol>
     *   <li>Unlimited shops short-circuit to {@code -1}, which
     *       {@link QSApi#processStockOrSpace(int)} maps to {@link Integer#MAX_VALUE}. Doing this
     *       first also removes the ambiguity in QuickShop's {@code -1} count-cache sentinel, which

     * which performs its own region hop and returns a future, and every other leg is either
     * already async or dispatched onto a virtual thread.
     */

            return CompletableFuture.completedFuture(-1);
        }

     * returns an already-completed future when we happen to own the region, and otherwise schedules
     * a {@code runAtLocation} task and completes from there. Its synchronous sibling
     * {@code getRemainingStock()} is just this method plus a 5-second blocking {@code join()},
     * so calling the async form and composing it is strictly better.
     * <p>
     * There is no {@code getRemainingSpaceAsync()} counterpart, so the sell path stays synchronous
     * and is dispatched onto a virtual thread instead.
     */
    private CompletableFuture<Integer> readLiveStockOrSpaceAsync(Shop shop, boolean toBuy) {
        if (toBuy) {
            return shop.getRemainingStockAsync()
                    .orTimeout(STOCK_READ_TIMEOUT_SECONDS, TimeUnit.SECONDS)
                    .exceptionally(ex -> {
                        Logger.logDebugInfo("Live stock read failed for shop " + shop.getShopId()
                                + ": " + ex.getClass().getSimpleName() + " - " + ex.getMessage());
                        return 0;
                    });
        }
        return VirtualThreadScheduler.supplyAsync(() -> getRemainingStockOrSpaceFromShopCache(shop, false));
    }
```

```java
        ShopTrading, ShopDisplay, ShopPermission, ShopExtraHolder
```

`ShopMeta<U> extends ShopPrice<U>`, and `ShopPrice<U>#price()` returns `U`. `ContainerShop implements Shop<Double, Location>` — it is the only implementation QuickShop ships.

**But `ShopManager` was not updated to match.** `getAllShops()` still returns a raw `List<Shop>`, as do `getShop(Location)`, `getLoadedShops()`, and the rest. Because the elements are raw, every generic member erases: `price()` returns `Object`, not `Double`.

Do **not** attempt to parameterize our field and method signatures to `Shop<Double, Location>`. `List<Shop>` and `List<Shop<Double, Location>>` are unrelated types with no implicit conversion, so that change would force an unchecked cast at every single `ShopManager` call site and spread the problem across the class. The right move is the opposite: keep raw `Shop` everywhere, matching what the API actually hands us, and confine one unchecked cast to a single helper.

Revisit this if and when QuickShop parameterizes `ShopManager`.

## Deferred — not in this plan

Recorded here so they are not lost. Do **not** implement these as part of the tasks above.

> Numbering note: these are items 4 and 5 from the API review that produced this plan. They are not "Task 4 / Task 5" — Task 4 above is the changelog step and *is* in scope.

### Follow-up (review item 4): Replace `isOwnerHavingEnoughBalance` with `ShopPrice#canAfford(int)`

`isOwnerHavingEnoughBalance` (`QSHikariAPIHandler`) resolves the owner's world via `Bukkit.getOfflinePlayer(uuid).getLocation().getWorld()`, which returns null for most offline players; the method then logs and returns `true`, so the "owner is too poor to buy" filter silently does not run in the common case. `ShopPrice#canAfford(int)` and `getMaxAffordable()` (new in 6.3.0.0) do this correctly with the right world and currency. Adopting them also lets us delete the `getQuickShop()` helper and the `QuickShopBukkit` → internal `QuickShop` cast, removing our only reach into QuickShop internals.

### Follow-up (review item 5): `ShopState` filtering and dead-code removal

Two separate pieces:

1. **`ShopState` filtering.** `shop.shopState()` exposes `isTradingAllowed()`, `isFrozen()`, and `blockedReasonTranslationKey()` (the `FrozenType` replacement). We currently never check shop state, so `/finditem` lists frozen and disabled shops as if tradeable. Add `isTradingAllowed()` to the search predicate in `searchShops`.
2. **Dead-code removal.** `isQSHikariShopCacheImplemented` and `checkIfQSHikariShopCacheImplemented()` parse the QuickShop version string to detect a v6+ feature. We cannot link against anything below 6.2.0.11 anyway (`bukkitLocation()` did not exist before it), so the `false` branch of `getRemainingStockOrSpaceFromShopCache`, the `shopCache` `ConcurrentMap`, the `SHOP_CACHE_TIMEOUT_SECONDS` constant, and the `CachedShop` model are all unreachable. If any version check is still wanted, `QuickShopAPI#getSemVersion()` returns a proper `Semver` and replaces the `split("\\.")[0]` parsing.

### Explicitly rejected: `ShopQuery`

The 6.3.0.0 changelog headlines `ShopQuery`/`Filters`, but reading the source it is a plain `for` loop over `getAllShops()` applying `Predicate<Shop>` in sequence — no async, no index, no region-thread awareness — and `MaterialFilter` calls `shop.getItem()` inline, which in our case must run on the region thread. It is strictly less capable than our existing `searchShops(Predicate<Shop>, boolean, Player)`. Where its filters would be sugar, `ShopManager#getShopsInWorld(World)` and `getAllShops(UUID)` already exist and are better. Do not adopt it.
